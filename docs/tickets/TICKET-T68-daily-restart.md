# T68 — Ежедневный рестарт бота (cron, 05:00)

**Заведено:** 2026-10-20 21:15 MSK
**Решение оператора:** «ежедневный крон ночью в 5 утра»
**Статус:** ✅ **код реализован и задеплоен 2026-10-21** (`soft` / `process` /
`process+engine` через `BOT_REANCHOR_MODE`). Установку таймера на хосте
делает оператор — пример в `examples/systemd/`.
**Обоснование:** `docs/adr/ADR-0003-context-reanchoring.md`
**Зависит от:** T66.1 (якорное окно) — без него рестарт не даёт эффекта

---

## Зачем

С решением R-A (неделя от старта бота назад) окно **якорится при старте** и
не скользит. Бот помнит «всё, что было неделю назад при старте, плюс всё,
что произошло с тех пор». При длинном аптайме контекст растёт монотонно.

Ежедневный рестарт в 05:00 пересчитывает якорь — бот «забывает» всё старше
недели на момент рестарта. Это штатная гигиена памяти, а не аварийная мера.

## Recheck: рестарт чего именно нужно

> **Superseded by ADR-0003.** The short version: the window is a timestamp the
> bot computes locally, so no engine restart is ever required for context
> correctness. Restarting the engine is VRAM hygiene. And "the engine is
> stateless" is wrong as stated — llama.cpp holds a KV slot and with `--keep -1`
> retains the prompt — but LCP prefix matching is precisely what prevents the
> corruption that was feared here. Read the ADR rather than this section.

Оператор предположил, что нужен рестарт **и** llama («рестарт бота не
очистит контекст llm а только еще больше забьет его»).

**Проверено по коду — это не так:**

`call_llama.py:790`, тело запроса к llama:
```python
req_body = {
    "model": MODEL,
    "messages": msgs,
    "max_tokens": max_tokens,
    "stream": use_stream,
}
```

Ни `session_id`, ни `cache_prompt`, ни `id` в теле **нет**. `sid =
f'chat-{chat_id}'` (`call_llama.py:1396`) обслуживает только bash-песочницу
(tmux-сессии), до llama он не доходит.

**Следствие:** llama-server не держит серверный KV-кэш между нашими
запросами. Контекст приходит **целиком в каждом запросе** из SQLite. Поэтому:

| | Последствие |
|---|---|
| Рестарт бота | якорь пересчитывается, память обнуляется по правилу — **достаточно** |
| Рестарт llama | KV-кэш и так пустой между запросами — **не нужен** |

**Вывод:** `llama-qwen5090-256k.service` **не трогаем**. Он `disabled`
by design (оператор поднимает движок руками), и он не является частью этой
механики.

⚠️ Это поправка к выводу оператора, сделанному на основе гипотезы. Проверено
по коду 2026-10-20.

## Варианты реализации

| Вариант | Как | Плюс | Минус |
|---|---|---|---|
| **A. cron на хосте** | `docker restart tb-bot` в 05:00 | просто, видно в crontab | попадает в хост, не в git |
| **B. systemd timer** | unit + timer, `OnCalendar=*-*-* 05:00:00` | журналируется, `Persistent` | надо трогать systemd |
| C. watchdog в боте | фоновый asyncio-таймер | всё в проекте | сложнее, таймер в каждом профиле |

**Рекомендация: B (systemd timer).** Причина — тот же `Restart=no`
oneshot-юнит, что уже есть для compose; журнал и `Persistent=` (если ночь
пропущена — отработает при загрузке). Вариант A проще на пять минут, но
`cron` на хосте не версионируется.

## Правило проекта

> Не трогать systemd-юниты без явного запроса оператора.

Запрос **получен** (оператор назначил время). Тем не менее реализацию
делаю отдельным коммитом с явным обоснованием, чтобы её можно было откатить
без затрагивания кода бота.

## Что должно логироваться при рестарте

Чтобы крон был наблюдаемым, а не «а что-то там ночью происходит»:

```
[t65] context anchor reset: start=... window_start=... messages_in_window=...
```

Плюс предупреждение, если сообщений в окне много (признак, что рестарт
не помогает и нужен другой подход).

## Критерий приёмки

1. Бот перезапускается в 05:00 (±5 мин)
2. После рестарта якорь пересчитан
3. Сообщения старше недели не попадают в контекст
4. Сообщения в окне — попадают
5. Ничего не теряется в SQLite (trim снят — T67.1)

## Чего не делаем

- **Не рестартим llama** — она stateless между запросами (проверено)
- **Не удаляем БД** при рестарте
- **Не трогаем `systemd/llama-*.service`** — их нет в проекте и они вне зоны
- **Не ставим крон без бэкапа** — бэкап вне scope (решение оператора,
  забота system operator), но об этом нужно помнить при отладке
