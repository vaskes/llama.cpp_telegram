# T66 — Временной лимит контекста: неделя, а не счётчик

**Зависит от:** T65.3 (trim) — **прямой блокер**
**Base:** main `8069781`

## Суть (со слов оператора)

Если бот «помнит всё», то в какой-то момент всё в контекст не влезет (жёсткий
лимит 256k) и места на ответ не останется. Значит нужно управлять тем, что
загружать.

**Ключевая формулировка, которую надо сохранить дословно:**

> Не привязывать к штукам или токенам — жаркие дискуссии генерируют сотни
> сообщений. Никто не помнит, о чём говорил в телеграме позавчера. Эта инфа
> сотка. Достаточно правило: **загружать только диалоги не старше 1 недели.**

Плюс два жёстких требования:
1. **Картинки из истории не грузить.**
2. **Историю в SQL чистить НЕ надо** — оператор планирует использовать её для
   дообучения модели и генерации LoRA. История критически важна.

## T66.1 — Фильтр по возрасту в `get_messages`

**Приоритет:** высокий. Ядро всей фичи.

**Что сделать**

В `storage.get_messages` (`storage.py:504`) добавить фильтр по `created_at`.
Не `LIMIT`, а `WHERE created_at >= ?` — это принципиально разные вещи:

```
сейчас:  ORDER BY id DESC LIMIT 20      ← «последние 20 штук»
нужно:   WHERE created_at >= ANCHOR     ← «всё не старше якоря»
```

**Почему это лучше счётчика (и почему оператор прав):**
- Горячая дискуссия = 500 сообщений за вечер → все 500 входят, и это ОК.
- Молчаливый чат = 50 сообщений за месяц → войдут только свежие.
- Счётчик не умеет различать «болтали 500 раз в среду» и «50 раз за месяц».

**Якорное окно, не скользящее (решение R-A).** Граница вычисляется
**один раз при старте процесса**, не в каждом запросе:

```python
# module level, вычисляется один раз при импорте
CONTEXT_WINDOW_START = time.time() - CONTEXT_MAX_AGE_DAYS * 86400
```

и передаётся в `get_messages` как параметр.

**Почему это критично:** `time.time() - 7d` внутри запроса дал бы
скользящее окно — противоречит решению оператора и тихo ломает семантику
«подгрузка при старте». Это ровно тот класс тихой подмены, который ловили
девять раз. Требует **tripwire-теста**: якор обязан быть константой модуля,
вычисленной один раз.

**Per-sub скоуп (решение R-B):** якор общий для процесса, фильтр
`chat_id = ? AND thread_id = ? AND created_at >= ?`. Разные subs считаются
независимо — активность соседнего sub не «состаривает» твой.

**Формат хранения времени:** `created_at REAL` — Unix timestamp. Фильтр
`created_at >= ?` индексируется, если добавить индекс (см. T66.2).

**Совместимость:** функция уже принимает `limit` — он остаётся как
**страховка сверху** (вдруг неделя даст 100k сообщений). Но это вторая
линия обороны, не основная.

**Критерий приёмки:** диалог двухнедельной давности не попадает в контекст;
диалог шестидневной давности попадает целиком, даже если это 500 сообщений;
при рестарте окно пересчитывается и «старое» забывается.

**Миграция:** `CREATE INDEX IF NOT EXISTS` — идемпотентна, безопасна на проде,
выполняется при старте. Данные не трогает.

## T66.3 — Картинки: НЕ СОХРАНЯТЬ (пересмотрено 2026-10-20)

**Приоритет:** снят — перенесён в **T67.2**.

**Было:** вырезать `image_url`-части при чтении истории (хранить, но не грузить).

**Стало по решению оператора:** картинки в базу **не пишутся вообще**.

> «картинки нахуй из базы, не сохраняем — они могут висеть в контексте бота

Обоснование выбора снимает вопрос о маркерах (`[image: подпись]` и т.п.) —

**Побочный эффект для T67:** это же решение закрывает второй вектор роста
БД. Base64-картинки были единственной причиной, по которой trim вообще
существовал. С их уходом trim теряет смысл полностью, а не «почти».

## T66.4 — Снять `TRIM_HIGH` (прямой блокер)

**Приоритет:** 🔴 **блокирует всё остальное в T66**

Оператор явно сказал: историю в SQL чистить не надо, она пойдёт в дообучение.
А `storage.py:139` `TRIM_HIGH=500` при 501 сообщении **молча удаляет** всё
сверх 200.

**Это прямое противоречие требованию.** Пока trim жив, «помнить всё» +
«использовать для LoRA» невозможно — часть данных уже стёрта безвозвратно.

**Что сделать:** убрать lazy-trim из `get_messages`.

**Почему безопасно:** SQLite на SSD держит миллионы строк без проблем. Для
чата ботов 10-50k строк — не нагрузка. Trim был нужен, когда история была
единственным, что занимало место; теперь картинки — вот где реально растёт
размер (см. T67).

## T66.5 — Конфигурация `bot_remember`

**Решение оператора** (2026-10-20): «не hardcoded параметр, пусть будет в
конфиге `bot_remember = 7d`»

**Что сделать:** параметр в конфиге, дефолт **7 дней**, имя в стиле
существующих — `BOT_REMEMBER_DAYS` (env) → `config.py` → якорь при старте.

**Правила (обязательны по проекту):**

1. **Не hardcoded** — значение только через config/env, дефолт в коде.
2. `0` или `-1` = без ограничения по возрасту (для отладки и для отладки
   датасета).
3. `.env.example` с комментарием-обоснованием. По правилу проекта:
   by-design решения документируются **рядом с кодом**, не в отдельном файле.
4. **Tripwire:** переменная есть в `.env.example` **и** читается в коде
   (класс дрейфа из T63).

**Семантика (обязательно задокументировать именно так):**

> `BOT_REMEMBER_DAYS` — это **длина окна памяти**, а не «сколько дней назад
> смотреть». Окно якорится в момент старта бота и не скользит.

Формулировка важна: без неё следующий читатель напишет
`time.time() - BOT_REMEMBER_DAYS` в каждом запросе и получит скользящее окно,
тихо противоречащее решению R-A. Это ровно тот класс тихой подмены, который
ловили девять раз.

**Вопрос закрыт:** 7 дней — значение по умолчанию, меняется конфигом.

## Решения оператора (2026-10-20)

**R-A. Неделя отсчитывается от старта бота назад.** Не скользящее окно.

> «неделя от старта бота назад, исходя из фичи — загрузка из sql lite при
> старте бота. этого достаточно, если бот долго не рестартовал он начнет
> галлюцировать при переполнении — это решается рестартом по крону»

**R-B. Скоуп per-sub.** Подтверждено.

### Что из этого следует (важно для реализации)

Окно **якорное, а не скользящее**. При старте в T0 запоминаем:

```
_CONTEXT_WINDOW_START = T0 - 7 * 86400
```

и далее фильтруем `created_at >= _CONTEXT_WINDOW_START` **навсегда**, до
следующего рестарта. Последняя точка — **не ограничена сверху**.

**Следствие, которое надо зафиксировать в коде:** при долгом аптайме
контекст растёт монотонно и **не имеет верхней границы по времени**. Бот
не «помнит неделю» — он помнит «всё, что было неделю назад при старте, плюс
всё, что произошло с тех пор».

Это осознанный размен оператора: галлюцинации при переполнении лучше, чем
потерянное «помню всё». Но это **системный риск**, а не частный, и он обязан
быть виден в коде:

1. Значение окна — **модульная константа, вычисляемая один раз при старте**,
   не `time.time() - 7d` в каждом запросе. Иначе получится скользящее окно,
   противоречащее решению.
2. Нужна **наблюдаемость**: сколько сообщений попало в контекст, какой
   возраст самого старого. Без этого переполнение приходит сюрпризом.
3. `CONTEXT_MAX_AGE_DAYS` в конфиге — это параметр **длины окна**, а не
   «сколько дней назад смотрим». Документировать именно так, иначе
   следующий читатель перепутает и сделает скользящее.

### Зависимость: рестарт по крону

Оператор указал его как решение переполнения. **Не реализую без отдельного
запроса** — это затрагивает systemd/host, а проектное правило прямо запрещает
трогать systemd-юниты без явного поручения.

Выносится в **T68** как отдельный тикет со списком вариантов
(systemd timer на контейнер / watchdog внутри бота / cron на хосте).

**Важно для проектирования:** до T68 в контексте не будет верхней границы,
и при аптайме длиннее нескольких дней переполнение реально. Значит
**обязательна** обработка ошибки «context overflow» от llama — сейчас
`call_llama.py` ловит её только в двух местах (`:1138`, `:1536`) и, судя по
коду, проглатывает. При переполнении бот должен сказать «контекст
переполнен, нужен рестарт», а не молча галлюцинировать. Это отдельная
подзадача **T66.6**.

### Открытый вопрос: гарантированный минимум (оператор: «не понял», требует пояснения)

**Ситуация, из которой он вырос.** Бот стоял неделю без рестарта. Утром
пришло сообщение. Якор окна — от момента старта неделю назад. Фильтр
`created_at >= anchor` **пропустит** всё, что старше якоря, то есть может
не пропустить **ничего вообще**.

Формально это корректно по правилу «неделя от старта». Практически — бот
выглядит сломанным: пользователь пишет, ответа нет, потому что в контексте
пусто.

**Что предлагается (на утверждение):**

Страховочный минимум — последние `BOT_REMEMBER_MIN` сообщений **всегда**
попадают в контекст, даже если старше якоря.

```
если сообщений в окне меньше BOT_REMEMBER_MIN:
    взять последние BOT_REMEMBER_MIN (без фильтра по дате)
иначе:
    взять всё в окне
```

**Почему это нужно:**
- Аптайм длиннее недели без рестарта → сейчас бот «забывает всё» и выглядит
  мёртвым.
- Крон в 05:00 (T68) это **смягчает**, но не гарантирует: если бот упал в
  04:00 и не поднялся до 05:00, или рестарт не сработал — та же ситуация.
- Для Lora-обучения полная история в БД остаётся в любом случае — страховка
  касается только выдачи в контекст.

**Почему это не очевидное «надо»:** оператор сознательно выбрал строгое
правило «неделя от старта» и принял побочные эффекты. Страховка — это
смягчение, которое **само по себе нарушает** его решение, если применять
всегда. Поэтому и спрашиваю, а не делаю.

**Значение по умолчанию при отсутствии ответа:** не добавлять. Пусть будет
строго как решено. Ответ нужен только если планируется аптайм длиннее недели
между рестартами (а он планируется — крон ежедневный, значит обычно ок).

## T66.6 — Обработка переполнения контекста (добавлена 2026-10-20)

**Приоритет:** высокий. **Следствие решения R-A.**

Оператор принял, что при долгом аптайме бот «начнёт галлюцинировать при
переполнении». Но рестарт по крону (T68) **ещё не существует**, а бот
работает. Значит переполнение — это текущая реальность, и оно должно быть
**видимым**, а не тихим.

**Факт:** в `call_llama.py` переполнение упоминается только в двух местах
(`:1138`, `:1536`) и там оно проглатывается — бот не сообщает пользователю,
что контекст исчерпан.

**Что сделать**

1. Поймать ошибку переполнения от llama (HTTP 400 с характерным телом).
2. **Сказать пользователю прямо**: «контекст переполнен, нужен рестарт бота».
3. Не выдавать заполненное галлюцинацию. Текущее поведение — тихо продолжить
   генерацию — хуже явной ошибки.
4. Логировать: сколько сообщений ушло в запрос, сколько токенов,
   возраст самого старого.

**Почему это отдельная задача, а не часть T66.1:** даже при правильной
неделе контекст может переполниться по другим причинам (длинное сообщение,
много картинок в одном запросе). Абсолютной гарантии «не переполнится» нет,
поэтому обработчик нужен **всегда**, а не только пока крона нет.

## T66.7 — Наблюдаемость окна

**Приоритет:** средний.

Раз окно якорится при старте и не скользит, оператор должен видеть, что
происходит. Расширить `/stats` (или лог при старте):

- время якоря окна;
- сколько сообщений попало в последний запрос;
- возраст самого старого сообщения в контексте;
- предупреждение при приближении к 256k.

Без этого переполнение приходит сюрпризом — и оператор не сможет проверить,
что неделя работает правильно.

## Чего не делаем

- **Не удаляем историю из SQL** — прямое требование оператора, для LoRA.
- **Не считаем токены** — оператор отверг, это бессмысленно при жарких дискуссиях.
- **Не фильтруем по размеру сообщений** — то же самое.
- **Не переносим картинки в файлы** — оператор отказался их хранить (T67.2).
