# T67 — Снос TRIM (первоочередной)

**Почему первое:** оператор планирует использовать историю для дообучения
модели и генерации LoRA. Пока trim жив, часть данных **уже стёрта
безвозвратно** — датасет получится дырявым.

## Что делает trim сейчас

`storage.py:139-140`: `TRIM_HIGH = 500`, `TRIM_LOW = 200`

`storage.py:525-540`, внутри `get_messages` — **лениво**, при чтении:
```sql
SELECT COUNT(*) FROM messages WHERE chat_id = ? AND thread_id = ?
-- если n > TRIM_HIGH:
DELETE FROM messages WHERE ... AND id NOT IN
    (SELECT id FROM messages WHERE ... ORDER BY id DESC LIMIT ?)  -- 200
```
Пока никто не читает — данные лежат. Стоит прочитать — 300 строк исчезают
без слова пользователю.

## Почему безопасно снести

| Масштаб | Строк в год |
|---|---|
| 20 сообщений/день | 7 300 |
| 200 сообщений/день | 73 000 |

SQLite на SSD держит это спокойно. `get_messages` идёт по индексу
`(chat_id, thread_id, id)` (`storage.py:89`) — стоимость выборки последних N
**не растёт** с размером таблицы.

Что реально росло — base64-картинки. Они уходят по T67.2, поэтому trim теряет
смысл **полностью**, а не «почти».

## T67.1 — Снос

1. Удалить блок trim из `storage.get_messages` (`storage.py:525-540`)
2. Удалить `TRIM_HIGH`/`TRIM_LOW` (`storage.py:139-140`) — иначе «мёртвый»
   код, который завтра кто-то включит
3. Починить **self-test** `bot.py:761-798` — он проверяет trim и упадёт.
   Заменить на проверку накопления без обрезки
4. Обновить доктринг `get_messages` — он описывает trim как фичу

## T67.2 — Картинки не сохраняем

**Решение оператора:** «картинки нахуй из базы, не сохраняем — они могут
висеть в контексте бота пока его не рестартанули, никакой боли в этом нет,
но хранить их не вижу смысла».

Не вызывать `_persist_message` для multimodal-сообщений (`handlers.py:445`).

⚠️ **Требует подтверждения.** Фраза «висеть в контексте пока не рестартанули»
неоднозначна:

- **Прочтение A:** картинка не в БД, но участвует в текущем обмене. В
  **следующем** запросе её уже нет — бот больше не может сослаться на неё
  через несколько сообщений. Сейчас умеет.
- **Прочтение B:** картинка держится в памяти до рестарта. Тогда нужен
  отдельный механизм in-memory кэша, которого в коде нет.

## T67.3 — Tripwire (обязательно)

AST/текстовый тест, падающий при возврате `DELETE FROM messages` или
`TRIM_*` в `storage.py`.

**Обоснование:** триггер возврата — не «кто-то полез сносить», а чтение
доктринга. Сейчас он прямо говорит:

> *"Lazy trim: if the row count exceeds TRIM_HIGH, prune down to TRIM_LOW.
> Self-throttling — bursts of activity do one trim and then no extra work."*

Кто прочитает это через полгода без git blame — решит, что trim нужен для
производительности, и вернёт. Тот же класс, что ловили девять раз: код
говорит одно, комментарий другое.

# T65 — Reply-to-human + подгрузка истории

## T65.1 — Reply-to-human: помнить, не отвечать

**Самый самостоятельный тикет. Можно начинать с него.**

### Что сейчас

`dispatch.py:1678` — `_is_reply_to_other_user` → `return` **до**
`process_update`, то есть до `persist()`. Проверено: reply-to-human **не
попадает в БД вообще**, не просто не отвечает.

### Что должно быть

| Ситуация | В БД | Генерация |
|---|---|---|
| reply на сообщение **бота** | ✅ | ✅ |
| **текст в чат** без reply | ✅ | ✅ |
| команда `/something` | ✅ | ✅ |
| **reply на сообщение человека** | ✅ **новое** | ❌ (сейчас) |
| private, любой reply | ✅ | ✅ |

### Тонкости

- Адресат берётся из `rtm.from_user` — уже разобран в `dispatch.py:1680`.
- Существующий `_tag_sender` умеет `From: {name}` — **переиспользовать**, не
  плодить новый формат.
- Лог `[dispatch] skipping reply-to-other-user` → переименовать: он больше
  не про skip, а про silent-absorb. Уровень INFO, не WARN.
- `_should_mute_in_group` (боты и `[llm]`-маркеры) **не трогать** — там
  глотать правильно, это другой механизм.

### Критерий приёмки

А пишет Б-у «дай код», Б отвечает А «вот» → бот молчит, но следующий запрос
от А показывает боту, что Б ответил А.

### Tripwire

AST-тест: ветка reply-to-human обязана вызывать `persist()` **до** раннего
выхода. Иначе «кто-то почистит» и вернёт тихое игнорирование.

# T66 — Временное окно: неделя от старта бота

## Решения оператора

**R-A. Неделя от старта бота назад.** Не скользящее окно.
> «неделя от старта бота назад, исходя из фичи — загрузка из sql lite при
> старте бота. этого достаточно, если бот долго не рестартовал он начнет
> галлюцировать при переполнении — это решается рестартом по крону»

**R-B. Per-sub.**

## Что следует из R-A

Окно **якорное**. При старте в `T0` запоминаем
`CONTEXT_WINDOW_START = T0 - 7*86400`, и фильтруем по нему **навсегда** до
следующего рестарта. Верхней границы по времени **нет**.

Бот помнит не «неделю» — он помнит «всё, что было неделю назад при старте,
плюс всё, что произошло с тех пор».

Три обязательных следствия:

1. Граница — **модульная константа, вычисляемая один раз при старте**. Если
   написать `time.time() - 7d` в запросе — получится скользящее окно, тихо
   противоречащее решению. Нужен **tripwire**.
2. Наблюдаемость обязательна (T66.7).
3. `CONTEXT_MAX_AGE_DAYS` — это параметр **длины окна**, не «сколько дней назад
   смотрим». Документировать именно так.

## T66.1 — Фильтр

`storage.py:504`, `get_messages`:
```
сейчас:  ORDER BY id DESC LIMIT 20      ← «последние 20 штук»
нужно:   WHERE created_at >= ANCHOR     ← «всё не старше якоря»
```

Принципиально разные вещи. Почему оператор прав: горячая дискуссия = 500
сообщений за вечер → все входят; молчаливый чат = 50 за месяц → только
свежие. Счётчик не отличает «болтали 500 раз в среду» от «50 раз за месяц».

- `created_at REAL NOT NULL` уже в схеме (`storage.py:86`) — **миграция не нужна**
- Per-sub: `chat_id = ? AND thread_id = ? AND created_at >= ?`
- `limit` остаётся как страховка сверху, не основная логика

## T66.2 — Индекс

Сейчас индекс только `(chat_id, thread_id, id)` (`storage.py:89`). Нужен
составной `(chat_id, thread_id, created_at)`. `CREATE INDEX IF NOT EXISTS` —
идемпотентна, безопасна на проде, выполняется при старте, данные не трогает.

## T66.6 — Обработка переполнения (добавлена после R-A)

Оператор принял галлюцинации при переполнении. Но **крона нет**, бот работает —
переполнение это текущая реальность, а не гипотетика.

Факт: в `call_llama.py` переполнение ловится только в `:1138` и `:1536` и
**проглатывается** — бот молчит вместо того, чтобы сказать «контекст исчерпан».

1. Ловить ошибку переполнения от llama (400 с характерным телом)
2. **Сказать пользователю прямо**
3. Не выдавать заполненное галлюцинацию
4. Логировать объём запроса

Отдельная задача, а не часть T66.1: переполнение возможно и при правильной
неделе (длинное сообщение, много картинок). Абсолютной гарантии нет —
значит обработчик нужен **всегда**.

## T66.7 — Наблюдаемость

Время якоря; сколько сообщений ушло в последний запрос; возраст самого старого;
предупреждение при приближении к 256k.

Без этого переполнение приходит сюрпризом и оператор не может проверить,
что неделя работает правильно.

## T66.5 — Конфигурация

`CONTEXT_MAX_AGE_DAYS`, дефолт **7**. `0`/`-1` = без ограничения (для отладки).
`.env.example` с комментарием-обоснованием (правило проекта: by-design решения
документируются рядом с кодом). Tripwire: переменная есть в `.env.example`
**и** читается в коде (класс дрейфа из T63).

**Вопрос:** 7 дней — навсегда или стартовое значение?

# T69 — Personality в system prompt (новое)

**Заявлено оператором:** «это переделка system prompt нужна текущего, и новый
injection в systemprompt — это bot personality (name, age, sex, profile и т.п.)».

## Recheck текущего состояния

| Параметр | Значение |
|---|---|
| `GROUP_CONTEXT` | **10 435 символов, 237 строк** |
| `RATING_RULES` | 2 463 символа, 63 строки |
| `WELCOME_TEXT` | 934 символа, 34 строки |
| Где вставляется | `call_llama.py:612`, `_group_ctx_msg` **на каждый запрос** |
| Тип | **константа** — не параметризована ничем |
| Personality | **отсутствует полностью** (grep: 0 совпадений) |

## Что это значит

10 КБ системного промпта уходит **на каждый запрос**, и **все** они
обслуживают одну сущность: групповую сцену `LlmChatPlace`. Первая строка:

> *«You are one of several LLM participants in a Telegram group called
> LlmChatPlace. Multiple humans and multiple LLM agents talk in the same room
> simultaneously.»*

То есть промпт написан для **обезличенного участника чата**. Ни имени, ни
характера, ни биографии. Для «одного из нескольких» это правильно, для
персонального бота — нет.

## Что предлагается

Разделить две сущности, которые сейчас смешаны в одной константе:

```
GROUP_CONTEXT  (сценарий: правила чата, tool-дисциплина, rating)
     +
BOT_PERSONALITY  (кто это: имя, возраст, пол, профиль, манера речи)
     +
[опционально] GROUP_PERSONA  (как вести себя в группе у людей)
```

**Источники конфигурации:** `config.py` → env-переменные
(`LLAMABOT_PERSONA_NAME`, `_AGE`, `_SEX`, `_PROFILE`…) → шаблон с подстановкой.

**Почему это редизайн, а не «дописать абзац»:**
1. `GROUP_CONTEXT` — **константа**. Чтобы параметризовать, нужен формат
   подстановки и место в `call_llama.py:612`, где собирается сообщение.
2. Промпт 10 КБ — половина может оказаться нерелевантной для персонального
   режима. Профили (public/personal/dev) уже есть в `limits.py` — промпт
   должен ехать из того же места.
3. Есть встроенный self-test на `GROUP_CONTEXT` (`bot.py:1856-1866`) — он
   сломается при смене формата. Надо чинить, а не обходить.

## Открытые вопросы

1. **Источник истины.** Personality живёт в репозитории (один бот — один

## ⚠️ Поправка к решению №6: llama рестартить НЕ нужно

Оператор вывел: «рестарт бота ≠ рестарт llama, рестарт бота только забьёт
контекст. Вывод: рестарт бота = restart current llm engine».

**Проверено по коду — зависимости нет.**

`call_llama.py:790`, тело запроса к llama:
```python
req_body = {
    "model": MODEL, "messages": msgs,
    "max_tokens": max_tokens, "stream": use_stream,
}
```

Ни `session_id`, ни `cache_prompt`, ни `id` в теле **нет**. `sid =
f'chat-{chat_id}'` (`call_llama.py:1396`) обслуживает только bash-песочницу
(tmux-сессии) и до llama не доходит.

**llama-server не держит серверный KV-кэш между нашими запросами** — контекст
приходит целиком из SQLite в каждом запросе. Поэтому рестарт **только бота**
достаточен, а `llama-qwen5090-256k.service` (disabled by design, ручной
запуск) трогать не надо.

## Пояснение к решению №2 (гарантированный минимум)

**Ситуация:** бот стоял неделю без рестарта. Утром пришло сообщение. Якорь
окна — от старта неделю назад. Фильтр `created_at >= anchor` не пропустит
**ничего**.

Формально корректно по правилу «неделя от старта». Практически — бот выглядит
сломанным: пользователь пишет, ответа нет, контекст пуст.

**Предложение (на утверждение):** последние `BOT_REMEMBER_MIN` сообщений
всегда в контексте, даже старше якоря.

**Против:** смягчение, которое само по себе нарушает строгое решение R-A.
Поэтому и спрашиваю. Дефолт при отсутствии ответа — **не добавлять**.

**Смягчает крон T68, но не гарантирует:** бот упал в 04:00 и не поднялся до
05:00 → та же пустая ситуация.

- **Рекомендация:** systemd timer, не cron на хосте — журналируется,
  `Persistent=` отработает если ночь пропущена
- **Логировать:** новый якорь, сообщений в окне, предупреждение если много

## Чего не делаем в целом

- Не чистим историю из SQL (прямое требование, для LoRA)
- Не считаем токены (оператор отверг — бессмысленно при жарких дискуссиях)
- Не поднимаем `CONTEXT_MESSAGES` «чтобы помнил»
- Не убираем разделение по `/sub` (оператор просил сохранить)
- Не трогаем systemd без поручения
- Не удаляем `_should_mute_in_group` и tool-whitelist (это безопасность)
