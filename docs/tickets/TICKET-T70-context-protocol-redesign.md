## Почему этот тикет переписан

Первая постановка была: «переделать так, чтобы движок держал сессии, бот
шлёт одно сообщение + `session_id`».

**Оператор отклонил** по фактам:
> «мы бота пишем в public репо, не только под себя. привязывать его к какому-то
> конкретному движку и его конкретной версии поддержки stateful API — затея
> пиздец сомнительная. ОСОБЕННО с учётом того, что главная задача llm engine
> быть stateless. А если я послезавтра захочу его со strata переключить на vllm?
> у меня на соседней машине как раз есть и две видеокарты и vllm. И это только я,
> а у нас есть ещё блять 200+ клонеров. В общем нам нужен универсальный путь»

Это не «передумал», это **новый факт, который меняет всё**: бот публичный,
движок — не наш компонент, а чужой. Значит архитектура обязана переживать
подмену движка без правок.

## Решение: паттерн, а не API

Индустрия в 2026 пришла к общему паттерну. Формулировка из документации
(LangChain / OpenAI cookbook / Microsoft Agent Framework / Anthropic
compaction — все независимо):

> **protect recent N · summarize older · extract durable facts · budget-assemble**

И, что важно, существует реализация, заявленная как
**provider-agnostic** (openai-agents-python issue #2244,
`LocalCompactionSession`):

```
SlidingWindowStrategy   — оставить последние N      (LLM не нужен)
SelectivePruningStrategy — выборочно удалить          (LLM не нужен)
SummarizationStrategy   — суммаризовать старое        (нужен дешёвый LLM)
HybridStrategy          — адаптивно по давлению      (опционально)
```

**Вывод: паттерн универсален, конкретные API — нет.** Значит берём паттерн,
пишем свою компактную реализацию.

## Что НЕ берём и почему

`vllm-project/agentic-api` (https://github.com/vllm-project/agentic-api) —
изучен, отклонён:

| Что это | Наш вердикт |
|---|---|
| Rust-шлюз (axum) перед vLLM | Отдельный сервис наRust в каждой инсталляции |
| OpenAI **Responses API** | Другой протокол, чем `/v1/chat/completions` |
| `previous_response_id`, Conversations API | Требует именно этого шлюза |
| Multi-agent steering, WebSocket lanes | Не нужно by design |
| OIDC, llm-d координатор, checkpoint лимиты | Избыточно для бота |

Их собственная формулировка подтверждает, что подход верный, но другой:
> *"The upstream inference call targets vLLM's own **stateless** Responses API —
> this project owns the state"*

Мы держим **тот же принцип** (state выше, engine stateless), но на
Python, в процессе бота, поверх обычного `/v1/chat/completions`.

## T70.1 — Скелет

**Создать `telegram-bot/context_budget.py`.**

**Почему отдельный файл, а не в `persistence.py`:** `persistence.py` сейчас
76 строк и делает ровно две вещи (persist/load). Стратегии сборки контекста —
другая ответственность, и они будут расти. Плюс отдельный файл тривиально
выпиливается, если клонеру он не нужен.

**Минимальный интерфейс:**

```python
class ContextBudget:
    """Assembles the message list sent to the engine.

    Engine-agnostic by construction: it never talks to an engine, it only
    decides which already-persisted messages to send.
    """
    def __init__(self, strategy: str, max_messages: int,
                 max_age_days: int | None = None, max_tokens: int | None = None):
        ...

    def apply(self, messages: list[dict]) -> list[dict]:
        """Return the subset to send. Must be pure — no I/O, no LLM calls
        (summarization happens in the caller and is passed in)."""
        ...
```

**Почему `apply()` чистая (без I/O и без вызова LLM):**
- Тестируется тривиально — обычный pytest, без сети и БД
- Стратегия `summarize` требует вызова LLM, а это делает **вызывающий** код;
  `apply()` получает готовую сводку
- Не тащит asyncio в чистую функцию

**Подключение — одна точка:**

```python
# persistence.py
async def load_history(chat_id, thread_id):
    rows = await asyncio.to_thread(get_store().get_messages,
                                   chat_id, thread_id, FETCH_LIMIT)
    msgs = _decode(rows)
    return _BUDGET.apply(msgs)
```

⚠️ **Важно:** `get_messages` сейчас принимает `limit` и режет в SQL. Для
стратегии по времени это неверно — сначала надо забрать всё в окне, потом
собирать. Значит `limit` становится внутренним (`FETCH_LIMIT` = страховка от
безумного объёма), а решение принимает `ContextBudget`.

**Обратная совместимость:** при `strategy="window"` и `max_messages=20`
поведение идентично сегодняшнему. Миграция безопасна.

## T70.2 — Стратегия `window` (дефолт)

Реализует решение оператора: **якорное окно, неделя, per-sub, не скользящее**.

```python
class WindowStrategy:
    """Keep messages newer than an anchor fixed at bot start.

    NOT a sliding window: `anchor` is computed once at process start and
    never moves. After a restart the anchor is recomputed, which is how
    the daily 05:00 restart (T68) resets memory.
    """
    def __init__(self, anchor: float): self.anchor = anchor
    def apply(self, messages): return [m for m in messages if m.created_at >= self.anchor]
```

**Требования:**

1. **Якорь — модульная константа, вычисляемая один раз при старте.** Если
   написать `time.time() - 7d` в каждом запросе — получится скользящее окно,
   тихо противоречащее решению оператора. **Это ровно тот класс тихих подмен,
   который ловили девять раз — нужен tripwire.**
2. **`created_at` должен попасть в сообщение.** Сейчас `get_messages`
   возвращает `{role, content, sender_name, rating}` — `created_at` не
   отдаётся. Добавить в SELECT.
3. **Per-sub:** `(chat_id, thread_id)` уже в запросе, стратегия про sub не знает.

**Конфиг:**

```
CONTEXT_STRATEGY=window        # window | summarize | hybrid
CONTEXT_MAX_MESSAGES=20        # страховка сверху (второй эшелон)
BOT_REMEMBER_DAYS=7            # длина окна, 0/-1 = без ограничения
```

**Tripwire (обязательно):** AST-тест, что якорь — константа модуля,
а не вычисление внутри запроса.

## T70.3 — Стратегия `summarize`

**Дефолтом НЕ включаем.** Но интерфейс должен позволять включить одной
строкой в конфиге — иначе это снова станет блокером.

**Алгоритм (по индустриальному паттерну):**

1. Разделить: свежие (в окне) / старые (за окном)
2. Свежие — в контекст как есть
3. Старые — если их много, отправить в дешёвый LLM с промптом
   «суммаризуй факты, решения, предпочтения»
4. Результат — **синтетическая пара** сообщений в начале:
   ```
   user:      «Сводка предыдущего разговора:»
   assistant: {summary}
   ```
5. На следующих вызовах использовать **уже существующую** сводку как базу
   (инкрементально, а не пересчитывать всю историю)

**Почему синтетическая пара `user→assistant`:** так делает OpenAI cookbook —
модель воспринимает это как завершённый диалог, а не как инструкцию.

**Что обязательно документировать в коде:**
- Сводка — это **производная**. SQLite остаётся источником истины
- Сводка может потерять детали → `/stats` должен показывать «сжато N из M»
- Если суммаризация падает (LLM недоступен) — **фолбэк** на `window`, не исключение

## T70.4 — Переполнение + наблюдаемость

Сейчас переполнение проглатывается (`call_llama.py:1138`, `:1536`) — бот
галлюцинирует молча.

**Что сделать:**
1. Ловить ошибку переполнения от движка
2. **Говорить пользователю прямо:** «контекст исчерпан»
3. Логировать: сколько сообщений ушло, сколько токенов, возраст старого
4. Счётчики в `/stats`: сколько в окне, сколько в БД, сколько сжато

**Почему это часть T70, а не отдельный тикет:** стратегия `window` защищает
по времени, но не по объёму. Одно сообщение на 200 КБ, или неделя активности,
или всплеск картинок — и 256k кончается. Обработчик нужен при любой стратегии.
