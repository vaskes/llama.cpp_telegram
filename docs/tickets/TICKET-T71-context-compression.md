## 1. Постановка оператора (словами, без пересказа)

> «Исходим из того что бот видит сообщения СТРОГО по одной штуке. Если мы
> будем ей передавать в LLM со всем обвесом (sender name,
> telegram_message_id и т.п.) по идее - все что у нее в текущем контекстном
> окне, она может аттрибутировать к телеге (tool delete message продолжит
> работать) и контекст будет расти нарастающим итогом, без захуяривания
> туда блоков по 64k контекста каждое новое сообщение. (правда мы тогда
> теряем деление контекста по subs, но я в принципе готов утратить эту
> фичу если мы сократим префилл на два порядка)»

> «Это серьезная переделка, надо на нее сделать бренч. отбренчевать,
> работать оттестировать и только потом мерджить.»

Плюс рамка, принятая ранее в этом же разговоре:

> «Мы ничего не инъектим каждый промпт в ЛЛМ» — то есть прошлого у модели
> нет **не из-за нашего кода, это ограничение Bot API**: бот получает
> апдейтами только НОВЫЕ сообщения, истории чата в Bot API нет вообще
> (`messages.getHistory` — «Only users can use this method»).

**Следствие, на котором стоит вся фича:** всё, что модель знает о
прошлом, — это то, что мы кладём в контекст. Значит, «история» — наше
изделие, а не слепок телеграма. Её можно сжимать без потерь.

## 3. Целевое состояние

```
  каждый ход:  system + tools
             + ОГЛАВЛЕНИЕ (все сообщения треда: id, автор, дата,
                           первые ~100-200 символов; append-only)
             + последние N сообщений ЦЕЛИКОМ
  по запросу:  до-чтение по id  ← новый тул
  в БД:        ничего не теряется; полный текст лежит, как лежал
```

## 4. Требования (проверяемые)

```
  R1  Оглавление вместо сырой истории: каждое сообщение в контексте
      представлено обвесом (id, автор, дата) + головой текста.
  R2  Последнее сообщение хода — целиком, всегда.
  R3  Атрибуция: у ответа бота появляется telegram_message_id
      (дописывается после отправки) и связь «ответ на сообщение X».
  R4  До-чтение: тул «прочитать сообщение по id» — полный текст,
      с явными лимитами.
  R5  Префикс-стабильность: оглавление append-only; «итог» НЕ
      пересобирается каждый ход (пересборка ⇒ reused 0 ⇒ всё насмарку).
  R6  Reuse жив: на втором ходе cached_tokens > 0.
  R7  БД цела: число строк и max(id) не уменьшились; ни одна строка
      не переписана по содержанию (служебные поля — можно).
  R8  Мультимодальность цела: image_url и документы не ломаются
      сжатием (content бывает JSON-массивом частей).
  R9  Telegram-tools работают: delete / react / search — регресс-тесты.
  R10 Дерево зелёное на каждом коммите; новый трипвайн + мутационный
      харнесс (группа A ловит, группа B снимает трипвайн ⇒ зелено).
```

## 6. Открытые вопросы (нужно решение оператора; мои варианты — в скобках)

```
  Q1  Суммаризация T70.5 — что с ней?
      (a) не трогать в этой ветке, вернуть как отдельную волну;
      (b) сделать её основой контекста (сводка + оглавление);
      (c) удалить как мёртвый код.
      Моя рекомендация: (a). Оглавление и сводка решают одну задачу
      двумя способами; смешивать их в одном контексте — два источника
      правды об одном и том же периоде.

  Q2  Деление контекста по subs (треды форума) — теряем или помечаем?
      Замер: тред 25 — 611 сообщений, тред 19 — 149, general — 9.
      (a) теряем: смешиваем всё в один контекст;
      (b) помечаем: "[thread 25]" в обвесе, 8 символов на сообщение.
      Моя рекомендация: (b). Сжатие не требует смешивания — фильтр по
      (chat_id, thread_id) уже есть в load_history, это один WHERE.
      Смешивание — отдельный выбор, и его цена: модель отвечает не
      в ту тему. Оператор был готов утратить — но цена не обязательна.

  Q3  Сколько сообщений держать в окне ЦЕЛИКОМ (N)?
      (5 / 8 / 15). Больше — съедает бюджет: при N=20 оглавление
      остальных 591 сообщения ≈ 28k ток, и сумма съедает всё.

  Q4  Что режем и до сколько?
      (a) только assistant-дампы (```bash), до 100-200 символов;
      (b) все сообщения длиннее порога;
      (c) только «консоль» внутри assistant-сообщений.
      Моя рекомендация: (c) — режем ровно те блоки, которые жгут
      токены (47 % промпта), и не трогаем обычную переписку.

  Q5  До-чтение: форма и лимиты?
      (сколько символов за одно чтение, сколько сообщений за раз,
      платит ли это бюджет хода). Нужно число: без него тул — открытая
      дыра в 40k.

  Q6  Где хранить id ответа бота?
      (a) UPDATE content (дописать маркер) — меняет байты контекста;
      (b) отдельная колонка — нужна миграция схемы;
      (c) только реестр собственных сообщений (он уже есть, переживает
          рестарт) — тогда в контексте маркера не будет.
      Моя рекомендация: (b) — маркер должен быть В контексте, иначе
      атрибуция своих сообщений не работает. Миграция — на 800 строк,
      это дешево, и нужна трипвайн «каждая строка читается».

  Q7  Старые строки без id (136 user-строк, до-введения колонки) и тред
      "selftest:" (14 строк) — удаляем? Оператор: «их можно удалить,
      они практической ценности не несут». Когда: отдельным шагом
      (с бэкапом) или в этой ветке?

  Q8  Селфтест пишет в прод-БД (136 строк: 'user query',
      'проверь математику', '/start', sender 'CUTOVER'/'V') — чинить
      здесь или отдельно? (Я бы отдельно, но не молча.)

  Q9  Правило сжатия для JSON-контента (image_url, документы):
      режем только текстовые части? Медиа не трогаем?

  Q10 Критерий «память не деградировала»: офлайн-реплей на живом
      движке — N вопросов о прошлом («что ты делал вчера?», «что
      показал тот ls?»). Согласовать список вопросов, иначе проверка
      на глаз.

  Q11 Дампы остаются в БД как есть? (Моё: да — это ответ бота, он в
      чате; сжатие только на выходе в движок.)

  Q12 Нужен ли в оглавлении фильтр «только тред N» или показываем
      тред в каждой строке?

## 8. Риски

```
  all-or-nothing префикса: любое per-turn изменение в оглавлении ⇒
      reused 0 ⇒ нужен трипвайн на байт-стабильность, а не на глаз.
      На сжатых формах reuse проверен (см. раздел 2), но это два
      одинаковых запроса подряд; живой ход добавляет новое сообщение
      в хвост, и префикс должен вырасти ровно на него.
  потеря деталей ⇒ модель «помнит оглавление, а не разговор» ⇒ без
      до-чтения фича бессмысленна (Q5)
  рост оглавления ⇒ fold ⇒ один дорогой ход (дешёвый, но нужен трипвайн)
  JSON-мультимодальность: content бывает не строкой, а массивом частей
  UPDATE своей строки (Q6a) меняет байты ⇒ ломает префикс между ходами
  «пересборка итога каждый ход» ⇒ reused 0 (прямое требование R5)
```

## 10. Порядок работ

```
  1. ветка + этот тикет в репо (первый коммит)
  2. трипвайн, красный на старом коде (без реализации)
  3. минимальная реализация: оглавление + последнее целиком +
     атрибуция + до-чтение
  4. мутационный харнесс (A/B), переякорение затронутых харнессов
  5. замер на живом движке: токены, reuse, холодное чтение, реплей
  6. доки + числа + CHANGELOG
  7. коммит с пинами релиза → тег → push → деплой → живой чек
  8. мерж в main после зелёного CI
```
