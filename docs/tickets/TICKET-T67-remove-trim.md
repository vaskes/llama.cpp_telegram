## Почему это первое

Требование оператора: история в SQLite нужна **целиком** — для дообучения
модели и генерации LoRA. Пока trim жив, часть данных **уже стёрта
безвозвратно**, и датасет получится дырявым.

Это не «ещё одна фича». Это **блокер качества данных**: остальные задачи
(T65, T66) будут читать из таблицы, которая молча самоуничтожается.

## Что делает trim сейчас

`storage.py:139-140`:
```
TRIM_HIGH = 500
TRIM_LOW  = 200
```

`storage.py:525-540`, внутри `get_messages`:

```sql
SELECT COUNT(*) FROM messages WHERE chat_id = ? AND thread_id = ?
-- если n > TRIM_HIGH:
DELETE FROM messages
 WHERE chat_id = ? AND thread_id = ?
   AND id NOT IN (SELECT id FROM messages
                   WHERE chat_id = ? AND thread_id = ?
                   ORDER BY id DESC LIMIT ?)   -- TRIM_LOW
```

**Ленивое** срабатывание: не при вставке, а при чтении. То есть пока никто
не читает — данные лежат. Стоит прочитать — и полусотня строк исчезают без
слова пользователю.

## Что сделать

1. **Удалить блок trim** из `storage.get_messages` (`storage.py:525-540`).
2. Удалить константы `TRIM_HIGH` / `TRIM_LOW` (`storage.py:139-140`) — иначе
   «мёртвый» код, который завтра кто-то включит обратно.
3. Обновить доктринг `get_messages` — он сейчас описывает lazy-trim как
   фичу. По правилу проекта: docstring рядом с кодом, без вранья.
4. **Починить self-test** в `bot.py:761-798` — он проверяет trim и упадёт.
   Заменить на проверку, что сообщения **накапливаются без обрезки**.

## Производительность — почему это безопасно

Trim был защитой от роста БД. Нужно убедиться, что без него SQLite не
захлебнётся.

**Расчёт для масштаба бота:**
- 20 сообщений в день → 365 → 7 300 строк в год
- даже 200 сообщений в день → 73 000 строк в год

SQLite на SSD держит это без единого напряжения. `get_messages` идёт по
индексу `(chat_id, thread_id, id)` (`storage.py:89`) — выборка последних N
строк по индексу, а не full scan. Стоимость **не растёт** с размером таблицы
для этой операции.

**Что действительно растёт** — картинки (base64 в `content`). Но по решению
оператора они в базу больше не пишутся (см. T67.2), так что этот вектор
закрывается тем же тикетом.

## T67.1 — Снос trim (основное)

**Файлы:** `telegram-bot/storage.py`, `telegram-bot/bot.py` (self-test)

**Критерий приёмки:** после 1000+ сообщений в одном `(chat_id, thread_id)`
все они читаются обратно; ни одна строка не удаляется.

## T67.2 — Картинки не сохраняем (сопутствующее)

**Решение оператора:** «картинки нахуй из базы, не сохраняем — они могут
висеть в контексте бота пока его не рестартанули, никакой боли в этом нет,
но хранить их не вижу смысла».

**Что сделать:** не вызывать `_persist_message` для multimodal-сообщений в
`handlers.py:445` (там base64 → `persist()`).

**Что это меняет по сравнению с моей прошлой постановкой:**

| | Было в T66.3 | Стало |
|---|---|---|
| Идея | вырезать картинки при чтении | не писать их вообще |
| Смысл | хранить и не отдавать | не хранить |
| БД | растёт от base64 | не растёт от картинок |

**Нюанс — РАЗРЕШЁН оператором** (2026-10-20):
> «бот при обработке подтянет ее в контекст обработает ответит ну и пусть
> висит в контексте. картинка в базу не сохранилась, при следующем рестарте
> бот не будет помнить что там было»

То есть прочтение **A**, без in-memory кэша: картинка участвует в текущем
обмене (модель видит, отвечает), в БД не попадает, после рестарта не
помнится. «Висит в контексте» = «в контексте этого запроса».

**Следствие для контекстного окна:** картинка учитывается только в том
запросе, где была отправлена. Через N сообщений бот о ней не вспомнит — и
это ожидаемо, не дефект.

## T67.3 — Tripwire на trim (обязательно)

**Приоритет:** высокий.

Trim — не «настройка», а **политика хранения данных**. Политики этого класса
не должны молча возвращаться.

**Что сделать:** AST/текстовый тест, который падает, если в `storage.py`
снова появится `DELETE FROM messages` или константы `TRIM_*`.

Обоснование — тот же класс, что мы ловили девять раз: код говорит одно,
комментарий говорит другое. Сейчас доктринг `get_messages` **описывает
trim как фичу** («self-throttling, bursts of activity do one trim»). Кто
прочитает это через полгода и не посмотрит в git blame — решит, что trim
нужен для производительности, и вернёт.

## T67.4 — Резервная копия перед сносом

**Оператор не просил, но это операция над единственной копией данных.**

Перед сносом: `sqlite3 conversations.db ".backup /opt/backup/...db"`.
Данные — append-only, trim никогда их не сжимал, но лишний бэкап стоит
0 ресурсов и снимает риск «а вдруг что-то сломалось при миграции».

**Сделать с осторожностью:** это прод-данные, бот работает.

## Порядок

```
T67.1 снос trim  ─┬─ T67.3 tripwire (в том же коммите)
                  └─ T67.4 бэкап (до)
T67.2 картинки не сохраняем  (сопутствующее, тем же тикетом)
```

**T67.1 + T67.3 — одним коммитом.** Удалить trim и поставить на него
tripwire. Иначе между коммитами существует версия, где trim удалён и не
защищён — ровно то состояние, в котором «кто-то почистит» и вернёт обратно.

## Чего не делаем

- **Не делаем `VACUUM`** — файловая база не сжимается автоматически, это
  отдельная операция и отдельное решение.
- **Не переносим картинки в файлы** — оператор прямо отказался хранить их.
- **Не меняем схему БД** — trim удаляется, а не заменяется. Миграция не нужна.
